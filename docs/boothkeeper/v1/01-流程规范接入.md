## 3. 方案与取舍

**选定：原样接入 ClaiDevSkill 的 dev-flow 规范（`devskill/` 逐字拷贝）+ 项目化 AGENT.md。**

| 备选 | 为什么不选 |
|---|---|
| 自建轻量流程（只加 CHANGELOG + 少量约定） | 无法解决「多机/多会话/多模型接手」问题；本项目已有「主上电脑 + 老公电脑 + 多个 Agent 会话」的真实并行场景，需要施工权唯一与 worklog 分文件机制 |
| 只写一份 docs/ 而不引入纪律与日志协议 | 纪律与日志协议正是本规范里最成熟的部分（第 0 铁律、双写顺序、插旗机制、恢复对账）。缺了它们，文档体系会在两周内退化为无人维护的空壳 |
| 照搬但改写 `DISCIPLINE.md` 适配本项目 | 规范明确要求「逐字拷贝、禁止改写」——现场改写会造成格式漂移，模板随之失效。项目特有规则一律进 `BOUNDARY.md` |
| 追补历史（为 1.0~1.5.6 补写需求文档与 worklog） | 历史 commit 与代码注释已承载绝大多数信息，追补成本极高且会引入推测性内容（违反「只写已发生、可复核的现象」）。**改为从现在起生效** |

**取舍说明**：
- 领域维度选 `docs/boothkeeper/`（单领域），不按 `docs/pi/`、`docs/architecture/` 多领域拆——本项目为单体桌面应用，多领域拆分会在当前规模下制造无谓的路径决策成本。规模显著扩大时再拆。
- 根目录存量脚本采**归档而非删除**：移入 `legacy/oneoff/`（保留可追溯），而非直接删。理由是本项目历史上出现过「按 R 号回溯当时的排障手段」的需求，且规范第 8 条要求清理前须用户确认。

## 4. 不做什么

1. **不重构 `booth_core.py`**（1418 行）的模块拆分。巨型模块确为技术债，但它不在本板块验收范围内，草率拆分会产生大量行为回退风险。
2. **不改动任何 UI / 主题 / 分类映射逻辑**。
3. **不做类型注解补全、不做 lint / formatter 引入**。属于独立议题，需单独立项。
4. **不删除任何历史 commit、不 force push、不重写 git 历史**。
5. **不触碰 BOOTH 真实资产库**（默认 `G:\Lin_File\BOOTH`）——所有验证走临时目录。
6. **不为 1.0~1.5.6 追补历史文档**（见 §3 取舍）。
7. **不引入 `booth-toolkit` 技能仓库的改动**（跨项目，属另一板块）。
