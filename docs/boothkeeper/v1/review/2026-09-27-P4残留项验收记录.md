## 二之二、中间提交可验证性（补齐 P3 的纪律偏离）

P3 登记过一处纪律偏离：红线「每项独立提交」未达成，当时以「按文件组的回退映射」作补偿。
本轮把它做对——拆为两次代码提交，并**逐点验证中间提交可独立通过**（否则「独立提交」只是形式）：

| 提交 | 内容 | 独立重跑结果 |

验证方式：`git worktree add --detach <sha>` 各取一个干净工作树，在其中独立重跑全套检查
（`git worktree remove --force` 已清理，验证后 `git worktree list` 仅剩主工作区）。

**为何把测试拆成两个文件**：单个测试文件跨两项改动时，`R24-1` 提交点的 `test_updater_diag`
用例必然是红的，中间提交无法验证，「独立提交」就退化为形式。拆开后每个提交点都能全绿。
代价是抽出共享辅助 `tests/_diag_capture.py`——`diag` 的 sink 是全局单接收方，两处测试需要
同一套接管/恢复逻辑，复制两份会漂移。

## 四、对归档记录推断的收窄（如实登记）

`review/2026-09-27-P3四项验收记录.md` §五-5 原文：

> `archive_item` 内 `bc.fetch_item` / `bc.classify_item_state` 未包 try：
> **网络异常会直接抛出**而非返回 `status=err`。

**实测收窄**：`fetch_item` 内部已有 `except Exception`，`probe_item_http` 与
`probe_reachable` 同样有兜底，故 `retry_request` 重试耗尽后抛出的 `ConnectionError`
**会被吞掉并返回 `None`**——真实网络故障下**不会**穿透至 `archive_item`。

因此本项的价值需要重新定位：**不在「修一个已知必现的崩溃」，而在终结「契约未声明、
调用方各自猜测」的状态**。支撑证据是实测的调用点不一致（3 个批量调用点中 2 个包了
`try`、1 个没包），以及「只要契约不明确，第 4 个调用点还会猜错」的推论。

**为何仍然定级为高危**：危害的充分条件不是「异常必现」，而是「异常一旦发生即静默丢件」。
实测已证明该后果为真（4 件丢 3 件 + UI 悬挂），且修复成本极低（20 行包装 + 零侵入）。
