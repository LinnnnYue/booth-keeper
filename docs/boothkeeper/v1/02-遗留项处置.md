## 2.1 后台异常统一上报通道

### 现象

打包后的程序没有控制台。PyInstaller `--windowed` 模式下标准输出被丢弃，因此
`print()` 写下的告警**在用户机器上完全不可见**。

现状实测：全项目 `print(` 共 11 处，其中 10 处属告警/失败语义：

| 文件 | 处数 | 性质 |
|---|---|---|
| `booth_core.py` | 5 | 封面下载全通道失败、错位扫描失败、旧版本隔离失败、图标契约校验失败等 |
| `archive_util.py` | 5 | 图标生成异常、归档中间态告警 |
| `pages/links_page.py` | 1 | 重试提示 |

`review/2026-09-27-静默失败点评审.md` §3 判定 8 处为「建议后续加固」，其**共同诉求
是同一条**：失败后界面呈现的状态与磁盘真实状态不一致，且没有任何出口可以让用户
或开发者知道「刚才有东西失败了」。逐处打补丁收益有限，根因是**缺少统一上报通道**。

### 目标

建立分级诊断通道，满足四条：

1. **逻辑层不依赖 Qt**。`booth_core.py` / `archive_util.py` 必须能在无 GUI 环境下
   被测试（当前测试网正是这么跑的），若为上报而 `import PySide6` 会破坏这一点。
2. **线程安全**。上报方是 QThread 内运行的 Worker，接收方是 GUI 线程，跨线程投递
   不得直接触碰控件。
3. **默认行为向后兼容**。未注册接收方时仍输出到 stdout，命令行/调试场景不退化。
4. **可回溯**。保留最近 N 条于环形缓冲，供日志面板一次性展示（用户事后排查用）。

### 方案与取舍

新增 `diag.py`（零新增依赖；**实施期修正**：立项估「约 60 行」，实测 115 行
—— 多出的是环形缓冲的线程安全封装与 sink 失败吞没，均为验收口径 1~4 的必需项），提供：

- `report(level, msg, scope="", **ctx)` — 唯一上报入口。`level ∈ {info, warn, error}`
- `set_sink(fn)` — 注册接收方；`fn(record: dict)`；传 `None` 恢复默认 stdout
- `recent(n)` — 取环形缓冲最近 n 条
- 内部 `threading.Lock` 保护缓冲与 sink 切换

GUI 侧在 `main_window` 启动时注册一个 sink，该 sink 只做一件事：把 record 经
`Signal(object)` 转发到主线程，由主线程写状态栏（error/warn 级）与日志面板（全级）。

**取舍一：为何不自建 `logging` 体系？**
`logging` 是标准库、更标准，但要满足上面四条仍需自定义 `Handler`（跨线程投递）
+ 自定义 `Formatter` + 环形缓冲（`MemoryHandler` 语义不匹配），配置代码量与本方案
相当，且引入 `logger` 层级/传播语义这类本项目用不到的复杂度。选定自研轻量通道，
换取「读一遍就懂、改一行就生效」。

**取舍二：为何不做文件日志？**
用户实际排障场景是「刚才那批归档有几件图标没生成」，属**近期、会话内**信息，
环形缓冲足够。落盘日志涉及轮转、路径、权限（Program Files 下不可写），
引入的复杂度与收益不成比例。留作后续可选扩展。

**取舍三：为何保留 `print` 兜底？**
`archive/scripts/` 下有历史脚本直接调用 `booth_core`，且开发者用 `python run.py`
调试时看 stdout 比看 GUI 面板快。默认 sink 保持 stdout，是刻意保留的双通道。

### 不做什么

- 不引入 `loguru` / `structlog` 等第三方日志库（违背「双击即用、零配置」定位）。
- 不做日志文件轮转与持久化。
- **不批量改写全部 `print`**。只改「失败/降级」语义的调用点；纯进度提示类
  `print` 保持原样（它们本来就不需要在 GUI 里看）。
- 不做日志级别运行时切换 UI（当前规模不需要）。

### 验收口径

1. 无 GUI 环境下 `diag.report("warn", "x")` 不抛异常，且被自定义 sink 收到。
2. 环形缓冲容量固定，超出后按 FIFO 淘汰最旧记录。
3. 跨线程上报（在 `QThread` 内 report）不崩溃、不丢消息，且 sink 在 GUI 线程被调用。
4. 未调用 `set_sink` 时，输出仍到 stdout（行为与改造前一致）。
5. 改造后 `py_compile` 全量通过，离屏启动无回归 —— 验收：
   `tests/_smoke_offscreen.py`（含 sink 收报计数与面板构建）。

**实施期补充的一项验收（立项时未列，实施中发现的缺陷场景）**：

6. **UI 未就绪时不得崩**。`main_window.load_config()` 在 `build_ui()` 之前执行，
   而配置损坏告警会触发 sink；若 sink 直接访问尚未创建的 `diag_btn`，会以
   `AttributeError` 反噬启动流程 —— 即「诊断通道自己成为故障源」。
   现行实现以 `getattr(self, "diag_btn", None)` 守卫，记录照常入缓冲与计数，
   仅跳过状态栏刷新。
7. **计数语义**：告警计数表示「未读」而非「累计」—— 打开面板即清零，
   面板内点「清空」亦清零（面板发 `cleared` 信号回主窗口）。否则该数字会
   伪装成「有持久故障」的噪音。

## 2.2 `force` 重归档回滚路径加固

### 现象

`archive_item()` 在 `force=True` 时采用「同位置日期留档」策略（R22，主上钦定）：
把 `dest` 现有内容整体移入 `dest/旧版本_<时间戳>/`，再落新内容。该路径有三处
**回滚失败静默点**（`review/2026-09-27-静默失败点评审.md` §4 判为高危）：

| 位置 | 语义 | 现行行为 |
|---|---|---|
| `archive_util.py` L285 | 留档中途失败 → 回滚已移入项 | 单项回滚失败静默 `pass` |
| `archive_util.py` L312 | 源不存在 → 还原留档内容 | 整体还原失败静默 `pass` |
| `archive_util.py` L349 | 移动失败 → 还原留档内容 | 整体还原失败静默 `pass` |

**为何判为高危**：这不是「没提示」，而是**给了错误的成功提示**。
L312 / L349 的返回消息写死「（留档内容已还原）」，但还原本身若失败了，
用户读到的是一句与磁盘状态不符的承诺。后果：用户以为商品还在 `dest` 根目录，
实际上它正躺在 `旧版本_<时间戳>/` 子目录里 —— 且触发条件（磁盘满、
文件被占用、权限不足）恰恰是用户最不会去核对目录的时候。

另有一处同源问题：三处回滚逻辑重复，`archive_item` 内部还有一份语义相近的
「还原已留档」代码，改动时容易只改一处。

### 目标

1. **如实上报**：回滚结果必须反映磁盘真实状态，返回消息区分「已完全还原」与
   「部分还原（N 项未还原，位于 <路径>）」。
2. **可观测**：回滚失败经 2.1 通道上报 `error` 级，而不是沉默。
3. **可验证**：失败场景必须能**脚本化复现**，否则无法证明加固有效。
4. **不改变既有策略**：留档行为本身（不删、不进回收站、标注日期永久留档）不变。

### 方案与取舍

**第一步：先建演练环境（不得跳过）。**
R17 时明确记录「未建演练环境前改动风险高于现状」，本次先补齐。用临时目录 +
故障注入构造四个场景：

| 场景 | 注入方式 | 断言 |
|---|---|---|
| 磁盘满 | monkeypatch `shutil.move` 抛 `OSError(28, "No space left")` | 返回 status=err，且消息与磁盘实际状态一致 |
| 文件被占用 | 目标文件以独占句柄打开后触发移动 | 同上，且不产生半截文件 |
| 进程被杀 | 模拟「留档完成但新内容未落」的中断点 | 重新归档可正确识别既有 `旧版本_*` 目录 |
| 半还原中间态 | monkeypatch 让回滚本身在第 2 项失败 | 消息报出「部分还原」，并给出未还原项位置 |

**第二步：提取回滚函数。**
把三处重复逻辑提为模块内私有函数
`_restore_from_archive(old_dir: Path, dest: Path, iid: str = "") -> tuple[int, list[str]]`，
返回 `(已还原数, 未还原项名列表)`；配套 `_describe_restore(restored, failed, old_dir)`
生成诚实措辞，以及 `_is_legacy_dir()` 供「不套娃」判定复用。三处调用点统一改用，
消除重复。

**第四步（实施期新增）：不套娃。**
三处调用点原以 `dest.iterdir()` 全量枚举待还原项，若 `dest` 内已存在
`旧版本_*` 目录（上次 force 的遗留），会被当作「待还原项」搬进新的留档目录，
形成嵌套。现以 `_is_legacy_dir()` 过滤，`旧版本_*` 一律不参与。此为
`test_04_中断态` 用例暴露的真实缺陷，非理论推演。

**第三步：消息按实际结果生成。**
彻底还原 → 现状措辞；部分还原 → 明确列出未还原项与所在路径，并经 2.1 上报 error。

### 不做什么

- 不改「同位置日期留档」策略本身（R22 主上钦定方案）。
- **不引入事务日志 / 回滚日志文件**。当前失败面已可通过「`旧版本_*` 子目录是否存在」
  推断，加一层日志属过度工程；若后续真出现「留档目录本身损坏」再议。
- 不改「移动失败时不删除任何东西」的既有安全取向（保持一件不丢）。
- 不做自动重试。回滚失败往往源于持续性条件（磁盘满），重试无意义且拖长时间。

### 验收口径

1. 四个演练场景全部可脚本化复现，且每个场景有明确断言 ——
   落地为 `tests/test_rollback.py`（5 个用例，见「实施期修正」）。
2. 加固后，三处返回消息在「部分还原」场景下**必须与磁盘实际状态一致**
   （验收方式：脚本比对「返回消息声称的还原数」与「实际位于 dest 根目录的文件数」）。
3. `_restore_from_archive` 提取后，`old_dir.rmdir()` 在 **代码中**仅 1 处
   （`archive_util.py` L216，位于该函数内），另 2 处为注释说明 —— 三处重复已消除。
   （**实施期修正**：立项时拟用 `rg "old_archived.rmdir"` 判定，实施时发现
   文本口径会把注释算进去，故改为「代码命中 1 / 注释 2」的精确表述。）
4. `BOUNDARY.md` B-1 合规：全部演练在临时目录进行，**不得触碰 BOOTH 资产库**。
5. 归档主流程（正常归档 / exists / mismatch / delisted）行为零回归 ——
   落地为 `tests/test_archive_flow.py`（6 个用例）。

> **实施期修正（2026-09-27）**：立项时列「四个演练场景」。实施时按
> 「能构造出独立断言」为标准复核，最终 **5 个用例** —— 原「文件被占用」与
> 「磁盘满」在注入层面同构（都是 `shutil.move` 抛指定异常），但受影响的
> **恢复分支不同**（前者命中 `PermissionError` 的原地重试语义，后者命中
> 空间不足的整体回滚），保留为两个独立用例以防后续分叉；
> 另有「源不存在」原属 2.2 现象表 L312 一行、未单独列为演练场景，本次补为
> `test_05`（它是唯一「留档完成但新内容从未落盘」的路径）。

## 2.3 QThread 样板提取

### 现象

项目有 11 个 `QThread` 子类，全部重复同一段装配：

```python
def __init__(self, ..., proxy, proxy_url, cookie):
    super().__init__()
    self.proxy = proxy; self.proxy_url = proxy_url; self.cookie = cookie

def run(self):
    s = bc.make_session(self.cookie)
    if self.proxy:
        s.proxies.update({"http": self.proxy_url, "https": self.proxy_url})
    ...业务...
```

分布：`search_page` 2 个（SearchWorker / ArchiveWorker）、`audit_page` 7 个
（ScanWorker / MismatchWorker / FixWorker / VersionWorker / FixMismatchWorker /
BackfillWorker / FixSysAttrWorker）、`links_page` 1 个、`dragdrop_page` 1 个。

> **实施期修正（2026-09-27）**：立项时记为「10 个 / 分布 2+5+1+1+另一处」。
> 实施时以 AST 全量枚举复核，实为 **11 个**，且 `audit_page` 是 7 个而非 5 个
> （立项时漏计 `ScanWorker`、`FixSysAttrWorker` 之外的两个）。本文件已按实测更正。
> 详见 worklog `[v1]-raphael-20260927-0230`。

**R17 漏改（本次新发现）**：这段手工 `s.proxies.update(...)` 绕过了 R17 建立的
`booth_core.apply_proxy()` 唯一真源。后果具体而现实：若用户在设置页清空了
「代理地址」输入框但忘了关开关（或配置文件里 `proxy_url` 为旧值），
`{"http": "", "https": ""}` 会**覆盖**全局映射，使请求既不走代理也不走直连的
预期分支 —— R17 收敛的真源在 Worker 路径上失效。

这使 T9 的剩余价值**未缩小**（`plan.md` P3 原注「剩余价值缩小」经复核不成立，
已在本次更正）。

### 目标

1. 抽出共享基类，消除 11 处重复的 session 装配。
2. **真正接入代理真源**：Worker 不再自持 `proxy` / `proxy_url` 参数。
3. 统一异常兜底：基类 `run()` 捕获未处理异常并经 2.1 上报，避免 Worker 静默死掉
   （当前只有部分 Worker 有 `except`，其余会直接崩在 `run()` 里）。
4. 保持各 Worker 业务逻辑与信号契约完全不变。

### 方案与取舍

新增 `pages/workers.py` 定义 `BoothTask(QThread)`（**实施期修正**：立项时拟名
`BoothWorker`，实施时定名 `BoothTask`。理由：它与 `QThread` 同层但语义更宽
——`needs_session = False` 的纯本地任务并不「务必有 Worker 会话」，
`Task` 比 `Worker` 更贴合；且避免与既有 `QThread` 子类命名风格混淆）：

- `__init__(self, cookie="")` 只保存 cookie；**不再接收 proxy 相关参数**
- `session()` → 返回 `bc.make_session(self.cookie)`，代理由 `bc` 全局真源统一处理
- 子类实现 `work(session)`（模板方法），基类 `run()` 负责建 session → 调 `work()`
  → 捕获异常 → `diag.report` + 发 `failed` 信号
- 基类**不**统一发射「完成」信号（**实施期修正**：立项时拟由基类统一 emit
  `finished`，实施时否掉。理由：各 Worker 的完成信号名与参数各不相同
  ——`finished` / `done` / `result`，参数有 `()` / `(int,)` / `(list,)` / `(dict,)`，
  且已被 UI 直接连线。强行统一即违反本项目标 4「信号契约完全不变」。
  改由各子类继续自持，基类只兜底异常出口 `failed`。）

**取舍：为何用模板方法而非 mixin？**
`QThread` 的 `run()` 是唯一入口，模板方法能保证「建 session → 异常兜底 → 完成通知」
三步对全部 Worker 一致，mixin 做不到强制。且子类只需把 `run` 改名为 `work`，
迁移机械、易审查。

**取舍：为何不并发化？**
当前串行归档是**有意设计** —— BOOTH 对高频请求会限流，且归档涉及大量磁盘移动，
并发收益低、风险高。本次不做并发改造。

### 不做什么

- 不改各 Worker 的业务算法与信号参数（UI 连接代码零改动）。
- 不引入 `QThreadPool` / `QRunnable`（现有 Worker 需要 `finished` 信号与对象持有，
  改造收益不抵风险）。
- 不做归档并发化。
- 不合并多个 Worker 为一个（它们生命周期与 UI 状态绑定方式不同）。

### 验收口径

1. `rg "s.proxies.update"` 在**代码路径**（非注释）命中 0（真源接入完成）。
   — **实施期修正**：立项时拟用纯文本 `rg` 判定。实施时发现该口径不可靠：
   文本检索无法区分代码与注释（基类说明性注释必然提到旧写法，会误报），
   且换个变量名即漏报。改为 AST 判定并落为常驻检查
   `tests/check_proxy_single_source.py`（含 1 条显式白名单 + 理由）。
2. 11 个 Worker 的公开信号名与参数不变 —— 验收：`tests/_compare_worker_contract.py`
   以 AST 比对改造前 commit 与工作区，逐类列出信号集差异（差异须为空）。
3. 离屏实例化全部页面无异常 —— 验收：`tests/_smoke_offscreen.py`。
4. 代理行为验证：配置 `proxy=True` + 空 `proxy_url` 时，Worker 取的 session
   走直连（`proxies == {}`），不再出现空值覆盖。见 worklog 实测四项。
5. 归档主流程集成测试结果与改造前一致 —— 验收：`tests/test_archive_flow.py`。

## 2.4 `booth_core` 单体拆分

### 现象

`booth_core.py` 1439 行，是项目最大文件（次大 `theme.py` 919 行纯样式）。
文件内部已有 `# ── 分段 ──` 注释边界，说明作者本就按模块思考，只是没落地为文件：

| 分段（行号） | 内容 | 规模 |
|---|---|---|

**取舍一：为何用门面重导出，而非改全部调用点？**
调用点遍布 5 个页面模块与 `archive_util.py`，且 `import booth_core as bc` 的写法
被 `archive/scripts/` 下历史脚本依赖。门面让「拆分」这件事对调用方**不可见**，
是风险最低的拆法。重导出在此处是**设计意图**，不是技术债 —— 需在门面文件头写明
这一意图，避免后人误判为冗余而删。

**取舍二：为何按既有注释边界拆，而不是更多/更少？**
以既有注释边界为准，不发明新边界（尊重作者已成立的世界线）。更细的拆分
（如把 `probe_*` 单独成文件）会带来循环导入风险，收益不抵成本；
更粗则在实施中被 620 行口径否决（见上「实施期修正」）。

**取舍三：门面为何用模块级 `__getattr__` 而非静态 `from x import *`？**
（**实施期新增取舍**）静态 `import *` 有两个具体缺陷：①`PROXY` 是**可变**模块级
变量，`apply_proxy()` 改的是 `bk_net.PROXY`，静态导入会让 `booth_core.PROXY`
变成一份**快照**，读写不一致；②私有名（`_json_cache` 等）不被 `import *` 带走，
跨模块引用会 NameError。`__getattr__` 动态转发使 `bc.anything` 恒等于其真源当前值，
且天然覆盖私有名。代价是 IDE 静态补全弱化 —— 已在门面文件头写明，且
`tests/check_module_deps.py` 以 AST 兜住未 import 的跨模块引用。

**取舍四：循环导入如何避免？**
严格单向依赖：`bk_domain` ← `bk_text` ← `bk_net` ← `bk_search` / `bk_local`；
`bk_shell` 独立（仅依赖标准库与 `PIL`）。`bk_domain.classify` 被 `bk_net` 使用，
方向是 net → domain，无环。

### 不做什么

- **不改任何函数签名与行为**。本次是纯机械搬迁，不改一个字符的逻辑。
- 不做「顺便优化」（如把 `requests` 换成 `httpx`、把 `Path` 用法统一）——
  搬迁与优化混在一起会让回归无法归因。
- 不追求「门面零重导出」（见取舍一）。
- 不改 `theme.py`（919 行但全是静态样式数据，拆它无收益）。
