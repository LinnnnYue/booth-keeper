## 3.1 `archive_item` 异常契约（高危）

### 现象

`archive_item` 从未声明「失败时是抛异常还是返回 `status=err`」。三个批量调用点
因此各自猜测，产生了**不一致的健壮性**。实测（`tests/_probe_batch_abort.py`，
注入点：第 2 件商品的 `fetch_item` 抛 `RuntimeError`，4 件投放）：

| 调用点 | `work` 内是否有 `try` | 实际处理件数 | `finished` 信号 |
|---|---|---|---|
| `pages/dragdrop_page.DragWorker` | **无** | **1 / 4** | **未发射** |
| `pages/search_page.ArchiveWorker` | 有 | 4 / 4 | 已发射 |
| `pages/audit_page.FixMismatchWorker` | 有 | 4 / 4 | 已发射 |
| 对照：`DragWorker` 不注入异常 | — | 4 / 4 | 已发射 |

`DragWorker` 的后果是双重的：

1. **静默丢件**——剩余 3 件不再处理，用户只看到进度停在 1/4，无任何「为什么停」的说明。
2. **UI 状态机悬挂**——`finished` 不发射，进度条与按钮状态不复位。

补充实测（`tests/_probe_exception.py`，`archive_item` 逐类注入）：

```
[穿透!!] fetch_item 抛 ConnectionError    -> 抛出 ConnectionError: net down
[穿透!!] fetch_item 抛 ProxyError          -> 抛出 ProxyError: proxy bad
[穿透!!] fetch_item 抛 Timeout             -> 抛出 Timeout: t/o
[穿透!!] fetch_item 抛 RuntimeError        -> 抛出 RuntimeError: boom
[穿透!!] fetch_item 返 None + classify_item_state 抛异常 -> 抛出 RuntimeError
[兜住]   download_cover 抛异常             -> {'status': 'ok', ...}（cover_ok=False）
```

**对归档推断的必要修正**：`fetch_item` 内部已有 `try`，故上表第 1~3 行在**真实
网络故障下不可达**——`retry_request` 重试耗尽抛出的异常会被 `fetch_item` 吞掉。
真实的可达面是**非网络异常**（第 4 行：解析失败、`rglob` 抛非 `OSError`、门面被
替换等）与**契约缺失本身**。因此本项的价值不在「修一个已知必现的崩溃」，而在
**终结「调用方各自猜测」的状态**：只要契约不明确，第 4 个调用点还会猜错。

底层函数另有一处 `try` 之外的行（`s = session or make_session()`，位于 `fetch_item` /
`probe_item_http` / `classify_item_state` 三处），实测 3/3 穿透。但在 Worker 路径下
`session` 恒由 `BoothTask` 传入，`or` 短路使该行不被执行，故**当前不可达**；
登记备查，不在本次改动（理由见「不做什么」）。

### 目标

把 `archive_item` 的契约从「未声明」改为**明确且可被依赖的一种**：

> **永不抛异常；无论内部发生什么，都返回一个含 `status` 字段的 dict。**

契约一旦明确，三个调用点的健壮性由被调方**统一保证**，不再依赖调用方是否记得包
`try`；未来新增的第 4、第 5 个调用点也自动受保护。

### 方案与取舍

**修根不修枝**：不动 `DragWorker`，而是在 `archive_item` 最外层统一收口。

```python
def archive_item(iid, root, session, move_source=None, force=False) -> dict:
    """（docstring 补写契约声明：永不抛异常，失败一律 status="err"）"""
    try:
        return _archive_item(iid, root, session, move_source, force)
    except Exception as e:
        diag.error(f"归档异常：{type(e).__name__}: {e}",
                   scope="archive_item", iid=iid)
        return {"status": "err", "msg": f"归档异常:{e}", "id": iid}
```

原函数体**整体改名** `_archive_item`，内部一行不改。取舍与理由：

**取舍一：为何在最外层收口，而不是给 3 个调用点补 `try`？**
现有 3 个调用点中 2 个已包 `try`，若在 `DragWorker` 也补一个，不一致确实消失——
但**只是这一批调用点暂时对齐**。契约仍未被声明，下一个调用点还会猜错。在最外层
收口把不变式固化在函数边界上，是本类问题的正解。且改动面最小：内部精细的
`status=err` 分支（留档失败 / 源不存在 / 建目录失败等）全部保持原样，外层兜底仅
处理它们**没覆盖到的**意外异常。

**取舍二：为何改名而非重写？**
改名 + 外层包装是**零侵入**：`_archive_item` 的 190 行逻辑（含 P3 刚加固的三处回滚
路径）一字不动，避免在加固过程中引入新回归。若采用「在原函数体内各处补 `try`」，
需改十几处，风险远高。

**取舍三：`except Exception` 是否过宽？**
此处恰恰需要过宽——目标是「绝不把异常抛给调用方」。`KeyboardInterrupt` /
`SystemExit` 不被 `Exception` 捕获，进程级中断仍可正常退出，语义正确。

**取舍四：兜底会不会掩盖真 bug？**
会，若静默返回。故**兜底必须留痕**（§3.2），这是本项的强制配套，不是可选项。

### 不做什么

1. **不给 `bc.fetch_item` / `bc.classify_item_state` 单独补 `try`**。最外层兜底已
   覆盖全部调用路径，逐一补属重复建设，且会让异常在更深处被吞、丢失 `iid` 上下文。
2. **不给 `DragWorker` 单独补 `try`**。治枝不治根；且 `ArchiveWorker` /
   `FixMismatchWorker` 里已有的 `try` 保留不动（无害冗余，改动面越小越好）。
3. **不改底层 `s = session or make_session()` 的位置**。当前不可达（见现象段）。
   P3 已确立「回滚类不可达路径先补演练用例再改」的纪律；此处同理——无演练场景的
   防御性改动会扩大回归面而无可验证的收益。登记备查。
4. **不改 `archive_item` 内部既有的 `status=err` 分支**。它们语义更精确（能区分
   「源不存在」与「建目录失败」），比外层兜底的统一文案有价值。

### 验收口径

1. 4 类注入异常（`ConnectionError` / `ProxyError` / `Timeout` / `RuntimeError`）下，
   `archive_item` 均**返回 dict 且 `status == "err"`，不抛异常**。
2. `fetch_item` 返 `None` 且 `classify_item_state` 抛异常时，同样返回 `status == "err"`。
3. `DragWorker` 在上述任一注入下：**处理件数 == 投放件数**，且 `finished` **已发射**。
4. **（防伪绿）** 兜底分支被执行过——以 `diag` 收到 `scope="archive_item"` 的 error
   记录为证，而非仅断言「没崩」。
5. 归档主流程 6 条路径（`ok` / `exists` / `mismatch` / `force` / `delisted` /
   连不上不妄断）行为**零回归**：`tests/test_archive_flow.py` 与
   `tests/test_rollback.py` 保持全绿。

## 3.2 兜底路径的可观测

### 现象

§3.1 的兜底若静默返回 `status="err"`，等于**用新静默换掉旧崩溃**：用户看到进度
推进了、UI 复位了，但那一件为什么失败仍不可知。P3 建立的诊断通道（`diag`）正是
为此存在，兜底路径必须接入。

### 目标

每一件被兜底捕获的失败，都能在诊断面板中被定位到**具体商品 ID** 与**异常类型**。

### 方案与取舍

兜底分支内调用：

```python
diag.error(f"归档异常：{type(e).__name__}: {e}", scope="archive_item", iid=iid)
```

- `scope="archive_item"` 与函数内既有的 4 处 `diag` 调用保持同一 scope 命名（该
  scope 已被 `diag.py` 的 docstring 举例使用，保持一致性）。
- `iid=iid` 进 `ctx`，诊断面板可按商品定位。
- 用 `error` 级（非 `warn`）：这是未预期异常，与「错位扫描未完成」这类预期降级不同级。

### 不做什么

不为兜底路径弹窗或写文件。弹窗会打断批量流程；文件日志见 §四-⑤。

### 验收口径

6. 注入异常时，`diag` 环形缓冲内存在 `level="error"`、`scope="archive_item"`、
   且 `ctx["iid"]` 等于被注入商品 ID 的记录。
7. 正常归档路径**不产生**新的 error 记录（无误报）。

## 3.3 `updater._resolve_proxies` 静默退化（低）

### 现象

`pages/updater.py` L26-32：

```python
if proxy is False:
    return None
try:
    from booth_core import proxy_map
    return proxy_map()
except Exception:
    return None          # ← 静默
```

`proxy_map()` 抛异常时代理解析结果静默变为「无代理」，更新检查转为直连。国内直连
GitHub 通常超时，最终 `check_update` 返回 `error`，`settings_page.check_update_now`
弹出：

> 检查更新失败 / 无法访问 GitHub API：网络失败或无法访问 GitHub / **请检查网络/代理设置。**

用户按提示去检查代理设置——但代理设置**可能是对的**，真正坏掉的是**代理配置的读取
环节**。这是**误导性反馈**：提示指向了错误方向，且真因无任何留痕。

**可达性**：低（需 `from booth_core import proxy_map` 成功而调用抛异常）。本项定位为
**防御性留痕**，而非修复必现缺陷。

### 目标

代理解析失败时留下可查痕迹，使「提示指向错误方向」这一情况在诊断面板中可被识别。

### 方案与取舍

`except` 分支内加 `diag.warn(f"代理解析失败，本次更新检查将直连：{e}", scope="updater")`，
返回值仍为 `None`（行为不变，仅增可观测性）。

用 `warn` 而非 `error`：这是**预期内的降级**（有直连兜底路径），不属未预期异常，
与 §3.2 的 `error` 区分。

### 不做什么

**不改 UI 提示文案**。「请检查网络/代理设置」在方向上是合理的——代理配置确实是
可能原因之一，把文案改成「代理配置读取失败」反而会在多数场景（真的只是断网）下
误导。正确做法是让**真因**进入诊断面板，由能看面板的人判断，而非改写给所有人看的
提示。

### 验收口径

8. `proxy_map` 抛异常时，`diag` 收到 `level="warn"`、`scope="updater"` 的记录，
   且 `_resolve_proxies()` 仍返回 `None`（行为不变）。

## 3.4 `parse_local_version` 全链失败无留痕（低）

### 现象

`pages/updater.py` L45-68 依次尝试三个版本来源（`_version` 模块 → `main_window.__version__`
→ `_version.py` 文件），全部失败时 `return "0.0.0"`——**无任何留痕**。

后果链条：`"0.0.0"` → `_parse_version("0.0.0")` = `(0, 0, 0)` → 与远端
`(1, 5, 1)` 比较恒为「有更新」→ 弹窗显示「当前版本：0.0.0 / 最新版本：v1.5.1」。
用户看到自己的版本是 `0.0.0`，无从判断这是真实版本还是读取失败。

反向场景同源：若远端 tag 解析也不出，`remote_v = ()` 为假 → `has_update=False`
→ 提示「已是最新 ✨」，而实际**根本没能比对**。这是**错误承诺**。

**可达性**：低（打包后 `_version` 模块存在；开发态 `main_window` 有 `__version__`）。
定位为防御性留痕。

### 目标

「三源全不可用」这一事实进入诊断面板，使 `0.0.0` 这个值可被识别为「读取失败」而
非真实版本号。

### 方案与取舍

在 `return "0.0.0"` 之前加一行：

```python
diag.warn("版本号三源均不可用，回落 0.0.0（版本比较结果不可信）", scope="updater")
```

**返回值不变**（保持向后兼容），仅增留痕。

前两级降级链（`_version` 模块缺失、`main_window.__version__` 缺失）**保持 `pass`
不加留痕**：打包态 `_version` 缺失与开发态 `main_window.__version__` 缺失都是
**正常情形**，打日志会产生持续噪音，反而淹没真信号。只有走到最后仍失败才是异常。

### 不做什么

不改 `_parse_version` 对 `"0.0.0"` 的解析、不改 `check_update` 的比较逻辑。
`0.0.0` 作为「未知」的哨兵值虽不理想，但改成 `None` 会波及 `check_update` 的返回
契约与两处 UI 消费方，超出本项范围。

### 验收口径

9. 三源均不可用时，`parse_local_version()` 返回 `"0.0.0"` **且** `diag` 收到
   `level="warn"`、`scope="updater"` 的记录。
10. 正常情形（`_version` 模块可用）下**不产生**该 warn（无误报）。

## 四、明确不做（3 项，附理由与依据）

### ① `bk_net.py` 仍是最大文件（449 行）—— 不做

**不做的理由**：P3 §2.4 已确立验收口径「各新模块 < 620 行」，449 行在口径内。
继续拆分的收益是「数字更好看」，成本是新增模块边界与循环导入风险，**收益不抵成本**。

**判据**：拆分的目的是**降低认知负荷与变更耦合**，不是追求行数指标。当前六个模块
已按职责分离（网络 / 搜索 / Shell / 本地 / 文本 / 领域），`bk_net` 承担的「会话 +
元数据 + 下载」三者共享同一套 `retry_request` / `session` 上下文，强行再拆会制造
跨模块往返。若未来 `bk_net` 自行增长越过 620 行，届时按同一套 AST 流程再拆。

### ② `diag` 只支持单接收方 —— 不做

**不做的理由**：`set_sink()` 的语义已明确为「替换」而非「叠加」，且当前**只有主窗口
一处接收方**。改成 handler 列表是为**一个尚不存在的需求**增加 API 表面积与并发
复杂度（多 sink 需各自处理线程亲和性）。

**判据**：P3 已实测验证当前设计满足全部验收项（环形缓冲 / 跨线程 sink / 未注册
回落 stdout / UI 未就绪不崩 / 未读计数语义）。**当且仅当**出现第二个真实接收方
（如落盘）时再改，属「按需演进」而非「提前建设」。

### ③ 无文件日志 —— 不做

**不做的理由**：P3 `02-遗留项处置.md` §2.1「不做什么」已明确排除，理由仍然成立——
写文件会引入新的失败面：安装目录只读（Program Files）、磁盘满、多实例并发写冲突、
日志轮转策略。这些成本换来的收益（可事后取证）在**有诊断面板**的当前阶段不成立。

**判据**：诊断面板已提供环形缓冲（500 条）供当场查看。若未来出现「用户不在现场、
需要事后取证」的真实诉求，再按 §3.3 的同一模式评估。

### ④ `updater.py` 另外 3 处 `except: pass` —— 不做

- **L52 / L58（`parse_local_version` 前两级降级）**：属**设计意图内的正常降级链**。
  `_version` 模块在开发态本就不存在，第二级同理。加留痕会制造持续噪音。
- **L87 / L98（`_fetch_html_tag` / `_fetch_api_release`）**：**已有上层可见反馈**。
  两函数的 `None` 返回值被 `fetch_latest_release` 汇总，最终由 `check_update` 转为
  `error` 字段，而 `settings_page.check_update_now` 对 `error` **有明确弹窗**
  （实测 L281-285）。用户主动操作有反馈，不属静默。

**判据**：静默失败点是否成立，判据是「失败是否影响用户可感知的状态承诺」，而**不是**
`except: pass` 的计数。上两类的失败都被上游正确消费，无状态承诺被破坏。
